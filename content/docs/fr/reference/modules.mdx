## Quinze clés obligatoires dès le premier module, et une facultative

Un module déclare `id`, `requires`, `schema`, `migrations`, `routes`,
`navigation`, `publicUrls`, `messages`, `emails`, `webhooks`, `jobs`,
`dataCategories`, `retention`, `purge` et `export`. Quitte à les laisser vides :
en ajouter une plus tard obligerait à rouvrir tous les modules déjà écrits.

Une seule clé est **facultative** : `seeds`, les données de démonstration du
module (ADR 069). Un module qui n'en déclare pas n'est pas incomplet — il est
silencieux, et le registre n'agrège que ce qui est déclaré. C'est la seule
exception, et elle est motivée : rendue obligatoire, elle aurait rouvert tous
les modules déjà écrits pour y poser un tableau vide.

## Quatre couches

`domain` porte les règles pures, `application` les cas d'usage,
`infrastructure` l'accès aux ressources extérieures et `presentation` ce qui se
rend. Les deux dernières ne s'importent jamais l'une l'autre, et c'est le lint
qui le refuse — pas la revue.

> Une règle qu'aucune commande ne vérifie est de la documentation, pas une
> règle.

## Générer, ne pas deviner

`pnpm ks scaffold <module>` produit un squelette conforme. Écrire le squelette à
la main est un signal.

Les modules activés se déclarent dans [`config/`](/docs/prise-en-main/configurer),
et le dépôt se lève avant tout le reste : [installer le dépôt](/docs/prise-en-main/installer).
